# Card: doc-to-data パイプライン（書類→AI抽出→正準データ→転記）

## 位置づけ
Arentの狩猟域（電気設備・空調＝高砂/大気社/きんでん/クラティア系）で反復する「書類地獄→データ化」の共通パターン。日々総合設備案件のA系（NTT定型書類）・B系（プラネスト見積もり）は、いずれもこの骨格を持つ。**個別ツールを都度作らず、この型に落とす。**

## 骨格
```
[元書類(バラバラ)] ─抽出→ [正準データ] ─検算→ [転記ドラフト(要確認フラグ付)]
                          ↑ここに溜まる = 代表の欲しい"ナレッジ/分析"の素
```

## 実測で確定した設計原則（2026-07 検証2本より）

### 1. 正準スキーマは2層にする（単層は破綻）
A系スキーマにB系を乗せたら、15フィールド中6がnull・10が意味ズレ。**単一の背骨には乗らない。**
```
共通コア(薄い)        : line_items[], tax, total, conditions[]   ← A/B両方で機能した
書類タイプ別プロファイル :
  A(工事/NTT)  → contractor(受注者), client_division, 工期, 直接工事費…
  B(見積/供給) → supplier, 宛先, 有効期限, 小計(機材費のみ)…
```
分析ゴール（代表の狙い）は共通コアの line_items に効くので、この2層でも死なない。

### 2. 各フィールドに value / confidence / source の3点セットを必須にする
- confidence: high / medium / low（lowは人の確認=HITLへ回す）
- source: どの書類のどこから取ったか（出典トラッキング）
- 元書類に無い項目は捏造せず value=null
- **AIの意味理解が効いた例**：工事場所=港区なのに発注区分=神奈川支店、の不整合をlowで検出。ルールベースでは拾えない。

### 3. 抽出の後ろに決定論的な検算層を必ず置く（勝ち筋はここ）
AIに「全部読めた？」と聞いても「読めた」と返す。全量でないことを検出したのは**Python検算（明細合計 vs 総括表）**。
- 明細合計 = 総括表の費目、税=税抜×税率、税込=税抜+税、を機械で照合
- **勝ち筋は賢い抽出ではなく、後ろの安い検算層**（多段推論ほど確度は落ちる）

### 4. 検算のテストケースに負値・割引・非課税行を最初から入れる
A系（工事積算）は明細が全て正値で、検算はきれいに通った。だが割引・非課税・マイナス行の挙動はA系だけでは一度も検査されない＝隠れ前提が残る。B系の値引き行を通して初めて、割引のエンコード揺れ（qty=-1 と 単価=-80000 で二重マイナス→符号が破綻）が表面化し、検算層がそれを「記載と不一致、要確認」として正しく捕まえた。
- 学び①：**割引/マイナス行は符号の入れ方が揺れる**。qty か unit_price のどちらか一方だけを負にする、と正準ルールを固定する
- 学び②：検算層の価値は「合ってる時に黙る」ことでなく「曖昧な行をHITLへ上げる」こと。値引き行はまさにそれを実演した
- 学び③：**1書類だけの検証は隠れ前提を残す。必ず種類の違う2つ目を通す**（これも今日の実測そのもの）

### 5. 役割語は書類の立場で意味が反転する
`contractor` はA系では受注者(自社)、B系では見積の宛先(発注側=自社)。同じ枠に入れると分析時に立場が混ざる。「自社から見た役割」を明示フィールドに持つ。

### 6. 転記物は"完成書類"でなく"要確認フラグ付きドラフト"として出す
岡島マネージャーの言う「記入漏れの確認」は、このフラグ層のこと。低確度・不整合・OCR疑いを転記物の末尾に列挙する。

## 候補OSS（8月に実データで評価する。未検証）
- ContextGem（`github.com/shcherbak-ai/contextgem`）: 抽出結果を原文にマッピングする参照機能＋根拠付けが組み込み。原則2と同じ思想が実装済み
- Unstract: PDF→JSON構造化をAPI/ETL化。溜めて分析へ、がプラットフォーム機能
- 一般に整った書類で85〜95%、手書き/劣化スキャンは以下。**AIは必ず外す前提で検算層を持つ**
